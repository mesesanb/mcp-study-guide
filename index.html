Lesson 1 · Introducing MCP

What MCP is and why it exists

Model Context Protocol (MCP) is an open standard for connecting AI applications to external tools and data. Think of it as USB-C for AI integrations: one plug shape instead of a custom cable for every device.

The problem it solves

Say you build a chat app and want Claude to work with GitHub. Claude can only act through tools, so you must write a tool schema and an implementation for each GitHub feature: repos, issues, pull requests, and dozens more. That is a lot of code to write, test, and keep current as GitHub's API changes.

Remember this sentenceMCP shifts the burden of defining and running tools from your application to specialized MCP servers.

Architecture: three roles

RoleWhat it isFrontend analogy
MCP host / your appThe application the user talks to (your CLI chat, Claude Desktop, an IDE)The web app
MCP clientCode inside the host that holds one connection to one serverfetch wrapper / API client class
MCP serverA program exposing tools, resources and promptsA backend service with a documented API

Common confusions the quiz likes

  • MCP does not replace tool use. Claude still uses tools. MCP only changes who writes and runs them. The two are complementary.
  • Anyone can write an MCP server. Service providers often publish official ones, so you reuse their work instead of writing your own wrappers.
  • MCP is a protocol (a spec), not a library. The Python and TypeScript SDKs implement it.
Exam angle"What is the main benefit of MCP?" Answer: you do not have to author and maintain tool schemas and functions for every external service yourself.
Lesson 2 · MCP clients

The client is the communication interface

The MCP client gives your application access to an MCP server. It sends requests, receives results, and hides the transport details from the rest of your code. Think of it as the typed API client in your frontend that wraps fetch.

Transport-agnostic

MCP defines the messages (the shape of requests and responses), not the wire they travel on. The client and server can talk over different transports:

TransportHow it worksWhen
stdioClient launches the server as a subprocess and talks via stdin/stdoutMost common for local dev, and what the course uses
HTTP (Streamable HTTP; older SSE)Server runs remotely, client sends HTTP requestsRemote and shared servers
WebSocketPersistent bidirectional connectionPossible, less common

The message types

Messages are JSON-RPC style request/result pairs. For tools the two you must know:

  • ListToolsRequest / ListToolsResult: "what tools do you have?"
  • CallToolRequest / CallToolResult: "run this tool with these arguments."

Resources and prompts have matching pairs (list, read, get). Servers can also push things back: log messages, progress notifications, and requests like sampling.

Full request flow (memorize this)

Exam angleClaude does not call the MCP server. Your application does, through the client, then returns the result to Claude as a tool_result.

Lesson 4 · Defining tools with MCP

Tools: let the model act

A tool is a function Claude can choose to call. In plain tool use you hand-write a JSON schema. With the MCP SDK you write a normal function and the decorator generates the schema from your type hints and Field descriptions.

Frontend parallel: it is like deriving a form's validation schema from a TypeScript type instead of writing both by hand.

Course tools: read_doc_contents (return a doc's text) and edit_document (find and replace a string inside a doc).

Python (course)
from mcp.server.fastmcp import FastMCP
from pydantic import Field

mcp = FastMCP("DocumentMCP", log_level="ERROR")

docs = {
    "deposition.md": "This deposition covers the testimony of Angela Smith, P.E.",
    "report.pdf": "The report details the state of a 20m condenser tower.",
    "spec.txt": "These specifications define the technical requirements.",
}

@mcp.tool(
    name="read_doc_contents",
    description="Read the contents of a document and return it as a string.",
)
def read_document(
    doc_id: str = Field(description="Id of the document to read"),
):
    if doc_id not in docs:
        raise ValueError(f"Doc with id {doc_id} not found")
    return docs[doc_id]

@mcp.tool(
    name="edit_document",
    description="Edit a document by replacing a string in its contents with a new string.",
)
def edit_document(
    doc_id: str = Field(description="Id of the document to edit"),
    old_str: str = Field(description="Text to replace. Must match exactly."),
    new_str: str = Field(description="The new text to insert"),
):
    if doc_id not in docs:
        raise ValueError(f"Doc with id {doc_id} not found")
    docs[doc_id] = docs[doc_id].replace(old_str, new_str)

if __name__ == "__main__":
    mcp.run(transport="stdio")
TypeScript (your stack)
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "DocumentMCP", version: "1.0.0" });

const docs: Record<string, string> = {
  "deposition.md": "This deposition covers the testimony of Angela Smith, P.E.",
  "report.pdf": "The report details the state of a 20m condenser tower.",
  "spec.txt": "These specifications define the technical requirements.",
};

server.registerTool(
  "read_doc_contents",
  {
    description: "Read the contents of a document and return it as a string.",
    inputSchema: { doc_id: z.string().describe("Id of the document to read") },
  },
  async ({ doc_id }) => {
    if (!(doc_id in docs)) {
      return { isError: true, content: [{ type: "text", text: `Doc ${doc_id} not found` }] };
    }
    return { content: [{ type: "text", text: docs[doc_id] }] };
  }
);

server.registerTool(
  "edit_document",
  {
    description: "Edit a document by replacing a string in its contents with a new string.",
    inputSchema: {
      doc_id: z.string().describe("Id of the document to edit"),
      old_str: z.string().describe("Text to replace. Must match exactly."),
      new_str: z.string().describe("The new text to insert"),
    },
  },
  async ({ doc_id, old_str, new_str }) => {
    if (!(doc_id in docs)) {
      return { isError: true, content: [{ type: "text", text: `Doc ${doc_id} not found` }] };
    }
    docs[doc_id] = docs[doc_id].replace(old_str, new_str);
    return { content: [{ type: "text", text: "Edited." }] };
  }
);

await server.connect(new StdioServerTransport());

Key points

  • Decorator = schema generator. No hand-written JSON schema.
  • Field(description=...) (or .describe() in zod) documents each parameter. Claude reads those descriptions to decide how to call the tool, so write them well.
  • The tool name and description are what Claude sees. A vague description means the tool gets misused or ignored.
  • Raise an error for bad input (Python ValueError). The error goes back to Claude so it can recover.
  • transport="stdio" means the server talks over stdin/stdout.
  • Do not print() to stdout in a stdio server: that stream carries protocol messages. Log to stderr. This is why the example sets log_level="ERROR".
Lesson 5 · The server inspector

Test your server without writing a client

The MCP Inspector is a browser-based debugger that ships with the SDK tooling. It connects to your server and lets you click through tools, resources, and prompts. Frontend parallel: it is Postman, or the React DevTools, for MCP servers.

Python
# run from the project root (with the venv active)
mcp dev mcp_server.py
TypeScript
npx @modelcontextprotocol/inspector node dist/server.js
  1. Run the command. The terminal prints a local URL (default port is 6274). Open it in your browser.
  2. Click Connect in the left panel. The status turns to "Connected".
  3. Open the Tools tab and click List Tools.
  4. Select a tool, fill in the parameters (for example doc_id), and click Run Tool.
  5. Read the result panel. Use it to confirm edits actually changed state, for example by running edit_document then read_doc_contents.
Why it mattersThe inspector is the fastest feedback loop. You debug the server in isolation before you write any client or chat code. Resources and Prompts get their own tabs once you define them.
Exam angle"How do you test an MCP server without building a client?" Answer: the MCP Inspector, started with mcp dev <server file>.
Lesson 6 · Implementing a client

Building the client wrapper

The SDK gives you a ClientSession that sends the MCP messages. The course wraps it in a small class, so the rest of the app calls client.list_tools() and never sees the protocol. Frontend parallel: an ApiClient class around fetch.

Python (course)
from contextlib import AsyncExitStack
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

class MCPClient:
    def __init__(self, command: str, args: list[str]):
        self._command, self._args = command, args
        self._session = None
        self._exit_stack = AsyncExitStack()

    async def connect(self):
        params = StdioServerParameters(command=self._command, args=self._args)
        read, write = await self._exit_stack.enter_async_context(stdio_client(params))
        self._session = await self._exit_stack.enter_async_context(ClientSession(read, write))
        await self._session.initialize()          # handshake: do this first

    async def list_tools(self):
        result = await self._session.list_tools()
        return result.tools                        # unwrap: result.tools

    async def call_tool(self, tool_name: str, tool_input: dict):
        return await self._session.call_tool(tool_name, tool_input)

    async def cleanup(self):
        await self._exit_stack.aclose()            # closes session and kills server process
TypeScript
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StdioClientTransport } from "@modelcontextprotocol/sdk/client/stdio.js";

export class McpClient {
  private client = new Client({ name: "cli-chat", version: "1.0.0" });
  constructor(private command: string, private args: string[]) {}

  async connect() {
    // connect() also performs the initialize handshake
    await this.client.connect(new StdioClientTransport({ command: this.command, args: this.args }));
  }
  async listTools() {
    return (await this.client.listTools()).tools;
  }
  async callTool(name: string, args: Record<string, unknown>) {
    return this.client.callTool({ name, arguments: args });
  }
  async cleanup() {
    await this.client.close();
  }
}

How it plugs into the chat loop

  1. App calls list_tools() and passes the tool definitions to Claude with the user's message.
  2. If Claude replies with a tool_use block, the app calls call_tool(name, input).
  3. The app sends the result back to Claude as a tool_result. Claude writes the final answer.
Exam angleTwo operations carry the tool flow: list tools and call tool. The client is also responsible for cleanup (closing the session and server process). Results come wrapped: you read .tools from a list result.
Lesson 7 · Defining resources

Resources: read-only data the app can fetch

A resource exposes data by URI, the way a GET endpoint exposes data by URL. The application decides when to read it. Claude does not call resources the way it calls tools.

Two kinds

KindURIExampleUse for
Direct resourceStatic, no parametersdocs://documentsOne fixed thing, such as the list of all doc ids
Templated resourceHas {params}docs://documents/{doc_id}Many items, fetched by id

The template parameter name must match the function argument name. The SDK extracts the value from the URI and passes it to your function. Frontend parallel: /docs/:docId in a router.

Python (course)
@mcp.resource("docs://documents", mime_type="application/json")
def list_docs() -> list[str]:
    return list(docs.keys())

@mcp.resource("docs://documents/{doc_id}", mime_type="text/plain")
def fetch_doc(doc_id: str) -> str:
    if doc_id not in docs:
        raise ValueError(f"Doc with id {doc_id} not found")
    return docs[doc_id]
TypeScript
import { ResourceTemplate } from "@modelcontextprotocol/sdk/server/mcp.js";

// direct resource
server.registerResource(
  "doc-list",
  "docs://documents",
  { mimeType: "application/json" },
  async (uri) => ({
    contents: [{ uri: uri.href, mimeType: "application/json", text: JSON.stringify(Object.keys(docs)) }],
  })
);

// templated resource
server.registerResource(
  "doc",
  new ResourceTemplate("docs://documents/{doc_id}", { list: undefined }),
  { mimeType: "text/plain" },
  async (uri, { doc_id }) => ({
    contents: [{ uri: uri.href, mimeType: "text/plain", text: docs[doc_id as string] }],
  })
);

Why the MIME type?

The mime_type is a hint to the client about what is inside, so it knows how to deserialize it. The course uses application/json for structured data (the id list) and text/plain for raw text.

Exam angleTools vs resources: if Claude must decide to fetch it, make it a tool. If your app fetches it for the UI or to enrich a prompt, make it a resource. Direct = static URI. Templated = URI with parameters.
Lesson 8 · Accessing resources

Reading resources from the client

The client sends a ReadResourceRequest with a URI. The result holds a contents list. You take the first item, check its MIME type, and parse accordingly.

Python (course)
import json
from pydantic import AnyUrl
from mcp import types

async def read_resource(self, uri: str):
    result = await self._session.read_resource(AnyUrl(uri))   # URI must be an AnyUrl
    resource = result.contents[0]                              # first item of the list

    if isinstance(resource, types.TextResourceContents):
        if resource.mimeType == "application/json":
            return json.loads(resource.text)                   # structured data
        return resource.text                                   # plain text
TypeScript
async readResource(uri: string) {
  const result = await this.client.readResource({ uri });
  const item = result.contents[0];
  if ("text" in item) {
    return item.mimeType === "application/json" ? JSON.parse(item.text) : item.text;
  }
}

Where it shows up in the app

  • Autocomplete. The user types @. The app reads docs://documents (JSON) and shows the ids as options.
  • Context injection. When the user sends "summarize @report.pdf", the app reads docs://documents/report.pdf and puts the text in the prompt. Claude never needs to call a tool to fetch it.
Why this beats a tool hereInjecting the content up front saves a round trip: no tool_use turn, no waiting for the model to decide to look.
Exam anglePattern to remember: result → contents[0] → check mimeType → json.loads or text.
Lesson 9 · Defining prompts

Prompts: expert instructions, packaged

A prompt is a pre-written, tested instruction template that the server author ships. The user triggers it, usually with a slash command. Frontend parallel: an editor snippet or a Slack /command.

Why not let users write their own? A server author who knows the domain can craft a prompt that works far better than a quick ad-hoc request, and every user gets the same quality.

Course example: a format prompt that tells Claude to rewrite a document in Markdown, using the edit tool to save the result. A prompt can take arguments (here doc_id) and returns a list of messages.

Python (course)
from mcp.server.fastmcp.prompts import base

@mcp.prompt(
    name="format",
    description="Rewrites the contents of the document in Markdown format.",
)
def format_document(
    doc_id: str = Field(description="Id of the document to format"),
) -> list[base.Message]:
    prompt = f"""
Your goal is to reformat a document to be written with Markdown syntax.

The id of the document you need to reformat is:
<document_id>
{doc_id}
</document_id>

Use the 'edit_document' tool to edit the document. After the document has been reformatted...
"""
    return [base.UserMessage(prompt)]
TypeScript
import { z } from "zod";

server.registerPrompt(
  "format",
  {
    description: "Rewrites the contents of the document in Markdown format.",
    argsSchema: { doc_id: z.string().describe("Id of the document to format") },
  },
  ({ doc_id }) => ({
    messages: [
      {
        role: "user",
        content: {
          type: "text",
          text: `Reformat document ${doc_id} using Markdown. Use the 'edit_document' tool to save the result.`,
        },
      },
    ],
  })
);

Test it in the inspector's Prompts tab: list prompts, pick format, enter a doc_id, and read the generated messages.

Exam anglePrompts are user-controlled, exist for common workflows, can take arguments, and return messages. Prompts and tools cooperate: the prompt tells Claude to use a tool.
Lesson 10 · Prompts in the client

Listing and using prompts

Two client calls: list_prompts() (what is available, for building the UI) and get_prompt(name, args) (fill in the arguments and get the messages back).

Python (course)
async def list_prompts(self):
    result = await self._session.list_prompts()
    return result.prompts

async def get_prompt(self, prompt_name: str, args: dict[str, str]):
    result = await self._session.get_prompt(prompt_name, args)
    return result.messages          # feed these to Claude as the conversation
TypeScript
async listPrompts() {
  return (await this.client.listPrompts()).prompts;
}
async getPrompt(name: string, args: Record<string, string>) {
  return (await this.client.getPrompt({ name, arguments: args })).messages;
}
  • The / command list in the CLI is built from list_prompts().
  • Argument values (like the document id) come from the user's selection and are passed in get_prompt.
  • The returned messages become part of the conversation sent to Claude. Claude may then call tools to finish the job.
  • The same document list from the resource (@ autocomplete) can feed the prompt's doc_id argument. All three primitives working together.

1. Startup (main.py)

  • Reads CLAUDE_MODEL and ANTHROPIC_API_KEY from .env and asserts both are set.
  • Starts the doc server as a subprocess: uv run mcp_server.py if USE_UV=1, otherwise python mcp_server.py.
  • AsyncExitStack plus async with on MCPClient guarantees every server process is closed on exit.
  • Extra servers can be passed as command-line arguments. Each becomes another MCPClient in the clients dict, so Claude can use tools from several servers at once.
  • CliApp.initialize() loads the doc ids (a resource) and the prompt list so autocomplete works.

2. The agent loop (core/chat.py)

while True:
    response = self.claude_service.chat(
        messages=self.messages,
        tools=await ToolManager.get_all_tools(self.clients),   # MCP list_tools, every turn
    )
    self.claude_service.add_assistant_message(self.messages, response)

    if response.stop_reason == "tool_use":
        results = await ToolManager.execute_tool_requests(self.clients, response)  # MCP call_tool
        self.claude_service.add_user_message(self.messages, results)               # tool_result back to Claude
    else:
        return self.claude_service.text_from_message(response)                     # done
// the same loop in TypeScript with @anthropic-ai/sdk
while (true) {
  const response = await anthropic.messages.create({
    model, max_tokens: 8000, messages, tools: await getAllTools(clients),
  });
  messages.push({ role: "assistant", content: response.content });

  if (response.stop_reason === "tool_use") {
    const results = await executeToolRequests(clients, response);  // client.callTool(...)
    messages.push({ role: "user", content: results });
  } else {
    return response.content.filter(b => b.type === "text").map(b => b.text).join("\n");
  }
}
Exam angleThe loop ends when stop_reason is not "tool_use". Tool results are sent back with role user as tool_result blocks. The loop is the app's code, not part of MCP.

3. ToolManager: from MCP tools to Claude tools

  • get_all_tools loops over every client, calls list_tools(), and maps each MCP tool into the shape the Anthropic API expects: name, description, input_schema (from MCP's inputSchema).
  • _find_client_with_tool finds which server owns the tool Claude asked for.
  • execute_tool_requests calls client.call_tool(name, input), keeps only TextContent items from result.content, json.dumpses them, and sets is_error from result.isError.

4. Resources in the app: the @ mention (cli_chat.py)

  • _extract_resources finds words starting with @, checks them against the real id list (the JSON resource), then fetches each match (the templated resource).
  • The content is wrapped as <document id="..."> inside a <context> block in the user message. The prompt tells Claude it does not need a tool to read the doc.
  • The @ is only a UI convention for mentioning. The real id has no @.

5. Prompts in the app: the / command (cli_chat.py)

async def _process_command(self, query: str) -> bool:
    if not query.startswith("/"):
        return False
    words = query.split()
    command = words[0].replace("/", "")                      # "/format report.pdf" -> "format"
    messages = await self.doc_client.get_prompt(command, {"doc_id": words[1]})
    self.messages += convert_prompt_messages_to_message_params(messages)
    return True                                             # skip the normal @-mention path
  • The server's prompt returns MCP PromptMessage objects. convert_prompt_messages_to_message_params turns them into Anthropic MessageParam dicts (role plus text).
  • The converted messages are appended to the conversation. The next loop iteration sends them to Claude, which then calls edit_document to apply the formatting.
  • Autocomplete for / uses list_prompts(). The prompt's description is shown as the menu hint.

Beyond the course · for extra depth

What else could appear

ScopeThis section goes past the course videos, based on the official MCP spec. Details like exact protocol revisions change over time. For the quiz, focus on the lessons above.

Under the hood: JSON-RPC and the lifecycle

MCP messages are JSON-RPC 2.0: requests have an id and get a response, notifications do not. A connection starts with an initialize handshake where client and server declare their capabilities (for example "I support tools and resources"). Only then do normal calls begin.

// what call_tool puts on the wire (simplified)
{ "jsonrpc": "2.0", "id": 7, "method": "tools/call",
  "params": { "name": "read_doc_contents", "arguments": { "doc_id": "report.pdf" } } }

Server-initiated features

  • Sampling: the server asks the client to run an LLM completion. Useful so a server needs no API key of its own.
  • Roots: the client tells the server which folders or URIs it may work in.
  • Logging and progress notifications: the server streams status to the client during long operations.
  • Elicitation: the server asks the user for more input mid-task.

Remote servers and security

  • Remote servers use HTTP transport and typically OAuth for authorization. Local stdio servers inherit the user's machine permissions.
  • Trust: tool descriptions and results are text that reaches the model, so a malicious server can attempt prompt injection. Only connect to servers you trust and keep a human confirmation step for risky tools.
  • Tool errors are returned in the result (isError) so the model can see and recover, rather than crashing the session.

Resource vs tool: when one is unclear

If it reads data and your app should control when, use a resource. If it has side effects, or Claude needs to choose it, use a tool. Many servers expose both for the same data.

Trick questions and common wrong answers

Tempting wrong answerCorrect
"Resources are controlled by the model."Resources are app-controlled. Tools are model-controlled.
"Prompts are written by the end user each time."Prompts are pre-written by the server author, triggered by the user.

"Claude connects directly to the MCP server."Your app, via the MCP client, talks to the server.
